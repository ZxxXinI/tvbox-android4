## OTA 与发布顺序

1. 提交并推送本轮源码；固定完整源码 SHA，为标签及 APK 内版本控制元数据的依据。
2. 启用原证书与强制签名配置构建 Release，核对实际 minSdk16、0.0.4/code4、不可调试及最低 API16 的 v1/v2 签名。
3. 与 GitHub v0.0.3 公开 APK 比较证书和版本码；原证书为历史调试证书，如实使用 `legacy-debug-release` 模式，不换证书。
4. 从实际 APK 生成五个公开附件：`app-release.apk`、`update.json`、`apk-info.json`、`signature.txt`、`SHA256SUMS`；私钥和口令不得进入仓库或附件。
5. 创建指向构建提交的 v0.0.4 标签，上传为草稿；核对附件后设为正式 Latest。
6. 匿名下载稳定 latest 清单与其中 APK URL，核对版本4、大小及 SHA-256；新旧签名一致及4>3满足覆盖升级条件。

设置 → 检查更新；或打开启动更新检查后重新启动。发现更新时由用户确认下载，APK 校验通过后打开系统安装器。API26+ 可能需允许“安装未知应用”；不是刷系统，也不是静默安装。

已安装本地 v0.0.4 测试包的用户不会得到同 code4 更新提示，可手动安装正式 v0.0.4 覆盖；旧正式 v0.0.3/code3 或更早版本可由原 OTA 清单发现 code4。系统安装器实机行为与升级后历史/来源保留仍需用户设备验证，公开下载与签名条件不等于已在投影完成 OTA 安装。
